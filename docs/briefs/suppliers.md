## Screen (master-detail, as the demo)
- Left: the supplier list (name, status badge, API type, open orders and "to review", success rate last hour, prepaid balance with the low-balance colour). Right: the selected supplier's detail. Selection in the URL: `/suppliers?supplier=<id>` (ARCHITECTURE §5.2; the dashboard links here); default the first supplier.
- Header actions as the demo: Connect supplier… (`POST /admin/suppliers`: name, driver/API type, base URL, username, API key (write-only: never shown again; the detail shows only the key's first characters if the DTO gives a hint), currency, limits; then offer "Test connection"), Test connection (`POST /:id/test`: show the server's result, e.g. account info or the failure text), Sync now (`POST /:id/sync`: services and balance; refuse while disabled as the demo does, but take the refusal from the server), supplier menu (Copy base URL, See its orders → `ordersListPath({ tab: 'all', supplierId: String(id) })` from `@/features/orders`, Disable… / Enable via PATCH `status`, Edit connection… via PATCH, Delete… via DELETE with the server's refusal shown).
- Detail: degraded/down banner, the four stats (success last hour with 24 h average, latency p50/p95, open orders with link, prepaid balance with runway text) from the supplier DTO and `GET /admin/reports/suppliers` (reports:read; spend, rejection rate, speed per supplier; hide the figures the staff member may not read). Charts with `LineChart` from `@/components/charts` (success rate and latency, last 24 h) when the DTO has an hourly history; otherwise omit them and log it. Services table (primary and fallback roles) with "Edit links…" (`PUT /admin/services/:id/supplier-links`: ordered supplier list for that service; catalog:update). API log (`GET /admin/supplier-api-logs?supplierId=`; newest first; a row opens `GET /admin/supplier-api-logs/:id` in a drawer with request and response bodies (pretty JSON, secrets already masked by the server); refresh every 10 s while the page is visible with a Pause toggle, as the demo's live log).
- Import services: "Import services…" (catalog:create) → `GET /:id/services` (the supplier's synced catalogue), pick items, **Preview** (`POST /:id/import/preview`: new, matching and changed services with the suggested price) then **Import** (`POST /:id/import`). Assumed bodies, logged.
- **Record top-up** has no route (the balance comes from the supplier through sync): drop it, offer "Sync now" instead, log the mismatch (the dashboard did the same).
- **Reroute open orders** (demo: to each service's fallback): the server has no bulk reroute. Port it as a dialog that lists this supplier's open orders (`listOrders` with `supplierId` and open statuses, from `@/features/orders`), lets the admin pick one target supplier (enabled, not down), then for each order calls `changeOrderSupplier` + `dispatchOrder` from `@/features/orders` one at a time with progress and a per-order failure summary (same rules as the orders feature's bulk reroute, `src/features/orders/hooks/useBulkSend.ts`: a 401 stops the run; a failed dispatch after a successful move says so). Log the mismatch (one target instead of per-service fallbacks).
