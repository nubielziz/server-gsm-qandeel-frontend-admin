# 024 One name per custom field

**Context.** A custom field of a service had three visible names in the console: a Key that staff had to type (and that could not safely change once orders used it), a Label that buyers read, and a Supplier key that said what the supplier receives and that was often left empty. Which of them a field was "called" depended on the screen, and an empty Supplier key quietly meant "use the key". The backend's decision 065 gives every field one Name: what a supplier receives, never empty, unique in its service without regard to letter case. The key stays in the database as a hidden identifier that the server makes from the Name when the field is created and never changes, so the answers stored with old orders still find their field. The console follows that model.

**Decision.**
- **The table.** The Custom Fields table of the edit view's Field part has the columns No., Name, Label, Type, Required, Pattern and Actions. The Key and Supplier key columns are gone. A row's inputs are named "Name of field N" and "Label of field N"; the Name is required ("Enter a name.") and the Label is optional, with the hint "Same as the name".
- **The hidden key.** A saved field's `key` is part of the form's values, with no input, and goes back in the body unchanged so the server recognises the field. A new row sends no `key`; the server makes it from the Name and answers it. Renaming a saved field keeps its key. `ServiceField` is now its own type (`key`, `name`, `label`, `fieldType`, `required`, `options`, `regex`, `isMainInput`) instead of a narrowing of the generated map row, and the body row is `ServiceFieldInput` (`key`, `label` and `isMainInput` optional).
- **The label.** The Label is sent as typed. An empty Label asks the server to store the Name, and a saved field's Label is always sent back, so staff who do not touch it keep what an import wrote.
- **Repeated names.** A name used by two rows, trimmed and without regard to letter case, is refused in the browser on the later row ("This name is used by an earlier field."), as the server does with 422 on `fields.N.name`. A server message about `fields.N.key` ("This field no longer exists. Reload the page.") or `fields.N.isMainInput` (a second main input) has no cell of its own and shows under the row's Name input; any other message the table has no input for stays in the section's failure line.
- **The main input.** The box a service's order is about (an IMEI, an account, a serial number) is a flag on one field, `isMainInput`, and a service has at most one. The table gets no column for it: the flagged row shows a small "Main input" badge beside its Name, and the Actions cell of every row gets one more icon button, first in the row, named "Main input of field N" and pressed when the field is the main input. Pressing it turns the flag on for that row and off for the others, and pressing it again turns it off. The body always carries `isMainInput`.
- **Order answers.** `GET /admin/orders/:id` now carries `answers: [{ key, label, value }]`, the buyer's answers to the service's custom fields. The order drawer lists one row per answer (label, then value) after the main input, replacing the single row that read a `device` text out of the order's inputs. The label and the value each read in their own direction (`dir="auto"`), because a buyer may type any script and a label may come from a supplier's text, and the value keeps the line breaks of a multi-line answer. When a service's main input is also one of its answers, the order's input is that answer's value, so the drawer leaves out the first answer whose text (trimmed) is the order's input instead of showing it twice. The type is `OrderDetail = Order & { answers }` and only the single read returns it; the list route and its rows are unchanged. The drawer shows the list row at once and the answers when the read arrives.
- **The mock layer.** The mock of `PUT /admin/services/:id/fields` plays the server's rules: a key made from the Name for a new row (lower snake case, `_2`, `_3` on a clash, `field` when nothing is left, a saved key never reused in the same save), an unknown key refused on `fields.N.key`, an empty, repeated or over-long (more than 120 characters) Name on `fields.N.name`, a second main input on `fields.N.isMainInput` ("Only one field can be the main input."), and the label and flag rules above. A made key stays within 60 characters (the base is cut so `_2` still fits), and on an IMEI service a row named IMEI in any letter case becomes the main input when no row is flagged. The mock of the single order read lists every stored answer that holds something, as text (a number or a flag spelled out, anything nested as JSON), in stored order: the label is "Device" for the demo's device text and the key itself for any other key, as the server does for a field its service no longer has. The demo's orders have no field definitions, so the mock cannot put the answers in form order as the server does.

**Consequences.**
- The wire changed: the fields body needs `name` and the rows carry no `supplierKey`. The console is released together with the backend change of decision 065; an older console cannot save fields against it, and an older backend rejects the new body.
- The wire is in MISMATCHES M368 (the fields) and M369 (the order answers); `docs/ASSUMED_CONTRACTS.md` has the new body.
- This change adds and removes no route. The route files generated from the backend's contract (`npm run mocks:live`) are made again once the backend carries decision 065.
- Left for later: the shop's checkout and merchant forms are not part of the console; they follow the same decision in their own repository.
