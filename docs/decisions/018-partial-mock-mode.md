# 018 Partial mock mode (`VITE_API_MOCKS=unbuilt`)

**Context.** The backend is built feature by feature. Today it serves `/health` and staff sign-in; access, merchants, wallets, ledger, currencies, audit logs and settings are being merged. Decision 014 gives two dev modes: everything mocked (`true`) or nothing mocked (`false`). With `false`, every page the backend has not built yet shows only its error state; with `true`, the console cannot talk to the real backend at all. The console has to run against the backend as it grows, without losing the mocked pages.

**Options.** (a) Keep two modes and switch by hand. (b) A third mode where each route goes to the real API when the backend has built it and to the mocks otherwise, decided per route. (c) A hand-kept list of live routes in the handlers.

**Decision.** (b), with the list generated from the backend's own contract (not kept by hand).
- Flag: `VITE_API_MOCKS=unbuilt` (dev server only). `true` and `false` behave exactly as before.
- Live list: `npm run mocks:live` (`scripts/gen-live-routes.mjs`) reads `$BACKEND_DIR` (default `../backend`)`/docs/contract/openapi.json`, takes the `x-gsm-key` of every operation (`METHOD /path/:param`), keeps what the console calls (paths under `/admin/` plus `GET /health`) and writes `src/mocks/liveRoutes.gen.ts` (`LIVE_ROUTE_KEYS`, committed). `npm run mocks:live -- --check` exits 1 when the committed file is stale. The lead re-runs it after each backend merge.
- Routing: `src/mocks/live.ts` turns each key into an MSW `passthrough()` handler (MSW uses the same `:param` syntax). `src/mocks/browser.ts` registers them before every mock handler (first match wins), so a live route never reaches its mock. Everything else stays mocked; `onUnhandledRequest` stays `bypass`. A passthrough request leaves the browser untouched, so it reaches the real API through the Vite dev proxy (`VITE_DEV_PROXY_TARGET`), on the same origin with `VITE_API_BASE_URL` empty. The patterns are exact (no leading `*`): `*/health` would also catch the mocked `/admin/system/health`. When `VITE_API_BASE_URL` is set, the patterns follow it.
- Session: the real session is an HttpOnly cookie that the mocks cannot see, and `/admin/auth/*` is live. So in this mode `guard()` lets every request through (the real API enforces sign-in on the routes it has built; the mocked routes are dev stubs) and `currentStaff()` answers seeded staff member 1. In `true` mode both are unchanged.
- Sign-in is real in this mode: the mock hint and the "mock data" footer badge show only with `true` (the badge says "partial mocks" here). Credentials and TOTP secrets: backend README, "Local sign-in".
- Safety: `main.tsx` starts the worker only when `import.meta.env.DEV` and the flag is `true` or `unbuilt`; `vite.config.ts` serves the worker script only for those two values and refuses both in a production build. `dist/` holds no mock code (checked: no `passthrough`, no `LIVE_ROUTE_KEYS`).

**Consequences.** One setting runs the console against whatever the backend has built, and the mocked pages keep working next to it. After each backend merge, re-run `npm run mocks:live` and commit the file; the more routes the backend builds, the fewer are mocked, until `false` is enough.
- A built `GET /resource/:id` also catches an unbuilt literal sibling such as `GET /resource/export`, because the route list only has the built keys. The real API then answers it (usually 404 or 422). This goes away when the backend builds the sibling, and the real API would route it the same way.
- A mocked page that calls a live route (for example a page that reads `/admin/auth/me`) now gets real data; mocked and real data can disagree (ids, roles). It is a dev tool, not a test double: tests still use the all-mocked layer.
