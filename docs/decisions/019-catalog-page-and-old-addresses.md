# 019 One Catalog page, Shop content, and old addresses that redirect

**Context.** The console had two pages for one job. Services & pricing held the services, their prices and rules; Storefront held the list of services on the shop, publishing and the retail price rules next to the shop's own content (landing pages, legal documents, help, the TAC catalogue, search). Staff moved between the two to answer one question about a service. Both names are also used outside the pages: the "g then p" and "g then t" jumps, the audit "Open record" link, the dashboard "Fix pricing" button, the palette, and stored links (an alert mail about a waiting retail price change, notifications in the bell, bookmarks).

**Options.** (a) Keep two pages and link them. (b) Merge them into a new feature folder and a new page. (c) Make the services page the Catalog page, keep the feature folder and its names, and keep Storefront as a smaller page for the shop's own content.

**Decision.** (c).
- The page is Catalog: resource `catalog`, path `/catalog`, heading and label "Catalog", icon `tag`, first in the Catalog group. The page manifest stays in the services feature (a manifest fills one page, and the feature keeps its folder and names). The page opens for any one of `catalog:read`, `pricing:read`, `inventory:read` and `storefront:read` (`PAGE_PERMISSIONS` in `src/features/services/lib/tabs.ts`, the one definition of the gate); each view then shows only what the role may read, and the server decides every call. The resource row keeps `catalog:read` as its own permission, which the manifest replaces, as for the other any-of pages.
- The old resource name `services` is gone as a page. A check by a name that matches no resource answers "allowed", so nothing may be left keyed by it: the shortcut map, the audit record targets and their access check, the dashboard button and the palette now use `catalog`, and tests assert that a shortcut names a real resource and that the audit link is offered to a role that may open Catalog.
- One builder, `catalogPath` in `src/features/services/lib/paths.ts`, writes every Catalog address: the table with its filters, a service panel (`open`, `section`), the Add services flow (`add`, `from`), the settings view with its tab (`view=settings&tab=…`) and the publish view with a run (`view=publish&run=…`). Links inside the app use it, so they never take a redirect: the page's own view, tab and run hooks, its header links, the storefront feature's `storefrontPublishPath`, `storefrontPricingPath` and `storefrontOnShopPath`, the audit and dashboard links. No other builder of Catalog addresses is left (the old `servicesListPath` is gone).
- Storefront keeps its name, path and shortcut and becomes "Shop content". It moves to the System group, right after Settings, because it holds the shop's own pages rather than anything about the services. Its gate loses `pricing:read`, which only opened the retail price rules that moved to Catalog. The Catalog group holds Catalog and Suppliers only. What stays in it is the shop's own content: the tabs Landing pages (the default, written into the address as `tab=landing` by every link and by the page itself), Content and legal, Help centre, TAC catalogue and Search. The listing dialogs, the publish runs and the retail price rules are still storefront components and are exported through its `index.ts`; the Catalog page mounts them, and the storefront's own tests mount them through a test-only stand-in route.
- **One shop switch per service.** A table row has one switch, "On the shop". A service that has a shop page (a listing) is switched on or off with `PATCH /admin/service-listings/:id`. A service that has none goes on the shop through a publish run of that one service, never through a console-made page: only the publish run sets the title, the web address and the shop price (by the shop price rules), checks the floor and the other conditions, and records what happened, so the switch and the bulk "Put on the shop" are one rule on the server and the console has no pricing or eligibility maths of its own. The switch reads the run until its preview is ready, applies it only when the server says the row is ready, reads it until it ends, and otherwise discards the draft and shows the server's reason with the next step. A service that cannot go on the shop says why in words beside a disabled switch (`shopBlocked`). Switching a page off needs `storefront:update`, switching it on also `storefront:publish`, a service without a page `storefront:create` and `storefront:publish`; each carries its permission hint. The bulk bar's "Put on the shop" splits the ticked rows the same way: one publish run for those with no page (a person confirms it in the publish view), a single call for each switched-off page.
- **A side panel beside the table, and the dialogs that stay.** `/catalog?open=<id>[&section=…]` shows one service in a labelled, non-modal side panel: beside the table from the `2xl` breakpoint (the table keeps a compact set of columns), in the table's place below it. Its sections are details, order form, suppliers, prices, shop page and activity; each control keeps its own permission and the server decides. The form of each dialog is lifted into a body that its dialog and its section share, so there is one form per job. The row menu and all its dialogs stay, a save made from a dialog refreshes the open panel, and a section with unsaved changes asks before the panel closes or the row changes.
- **Add services.** One flow, owned by the suppliers feature, opened by the Catalog header's "Add services" (`catalog:create`) or by `/catalog?add=<supplier id>&from=groups|services` (`add=new` starts with no supplier). The Catalog page mounts a host that reads and clears those two keys, takes the dialog as a prop and, for "A service of my own", closes the flow and opens the existing New service form (the old "New service" button is gone); when that form saves, the panel opens on the new service. Step 1 chooses where from (a connected supplier, then whole groups or single services, or a service of one's own). **Step 2 shows the server's figures and nothing else**: for groups what Quick add's review says, for single services the import preview with the suggested price of each row. It cannot choose a category or change a price, because the backend takes neither when a run starts; a new service lands in the category named after its group with the default minimum profit, and the shop price follows the shop price rules, and all of it can be changed afterwards in the panel, the bulk bar or the settings. Step 3 starts the run and shows its result in the dialog. Whole groups choose On sale or Switched off and the shop switch there; single services have only the shop switch, because the import takes no status and adds every new service On sale (M277), and switching them off afterwards is the row's "Enabled" switch or the bulk bar's "Switch off"; a publish run the console starts itself (the single-services path) never publishes without a person's confirmation, while on the groups path the server's own Quick add hand-over publishes the ready rows by itself when the shop switch is on. "Quick add…" and "Import services…" stay on the Suppliers page, unchanged, beside the new link "Add services from this supplier" (the same permission as Quick add).
- Old addresses redirect for good. One pure function, `legacyTarget` in `src/app/legacyRedirects.ts`, maps path and query to the new address or to nothing; `LegacyRedirect` runs it and replaces the entry. It wraps every page route (`/storefront` is still a real page) and has its own route for `/services`, so it runs before a page's permission gate. The query is carried; the table keeps only the keys it reads; `status=disabled` becomes `chip=off`. A `/storefront` address that names one of its own tabs, and the bare page, are never redirected; the old default tab of Storefront had no `tab` in its address, so it is told by `q`, `page`, `sort` or `dir` alone, which Shop content writes with its tab.

**Consequences.**
- A role with only `pricing:read` or `storefront:read` now opens Catalog and lands on the first view it may use, and a role with only `pricing:read` no longer opens Shop content. A role with none of the four read permissions still opens neither.
- The sidebar order, the palette's "Go to" rows and the first page a role without the dashboard lands on follow the order of the resource rows: Catalog and Suppliers in the Catalog group, Shop content between Settings and Audit log.
- The redirect table is data in the tests: a row per case in `legacyRedirects.test.ts`, and routed tests that assert the address, the replaced entry and that the gate answers for the new page. A change to an old address or to a Catalog address is a change to those rows.
- The backend writes `/storefront?tab=pricing` into its alert mails; that address keeps working through the redirect, so the mail needs no change in the same release.
- A new page that wants a retired address of its own adds a case to `legacyTarget` and a test row; nothing else in the shell changes.
- The Catalog table no longer has a "New service" button; every way to make a service starts at "Add services", and the header button and the Suppliers page's link only write or follow an address (`add`, `from`), so the flow can be opened from any link, a reload keeps it open, and closing it keeps the table's filters.
- The Add services flow cannot promise a category or a price for the services it brings in. The limit is logged in MISMATCHES (M273); a backend input for either would let step 2 offer the choice.
- The single-service shop switch makes a draft run and may discard it, so the publish history can show short-lived drafts; the table is refreshed once when the switch ends.
