# 022 Product / Services replaces the Catalog page

**Context.** Decision 019 made one Catalog page for services, their prices, the shop and the suppliers' additions: a table with chips, a side panel beside it, a multi-step dialog for adding services and a settings view of tabs. The owner asked on 2026-11-23 for the work done on the Catalog page to be removed completely and for a new page, **Product / Services**, to replace it. The new page follows the layout the owner asked for, in the console's own look (kit tokens, light and dark themes): a strip of tabs for the kind of service, under it a row of text links where every link is a whole view of the page (no dialog for a view, no side panel, no multi-step dialog), lists that end in a bar pinned to the bottom with the results, a page number box, the pager and the page size, and forms that end in a pinned action bar with one primary button.

**Decision.**
- **What the page is.** Resource `products`, path `/products`, heading and sidebar label "Product / Services", icon `tag`, first in the Catalog group (the group name stays; the group holds Product / Services and Suppliers only). The page manifest stays in the services feature (a manifest fills one page, and the feature keeps its folder and names). The page opens for any one of `catalog:read`, `pricing:read`, `inventory:read` and `storefront:read` (`PRODUCTS_PAGE_PERMISSIONS` in `src/features/services/lib/productsPage.ts`, the one definition of the gate); each view then shows only what the role may read, a link a role may not use is not drawn, and the server decides every call. The shortcut "g then p" and the palette's "Go to" row name the resource `products`; a name that matches no resource answers "allowed" in an access check, so nothing is keyed by `catalog` or `services` any more, and a test asserts both names are not resources.
- **Level 1, the kind.** `?type=imei|server|remote|file` (IMEI Service, Server Service, Remote Service, File Service; IMEI when the address names none). Everything below shows that kind only, except what has no kind (publish runs, the code list, the merchant price rules), which the strip does not narrow.
- **Level 2, the view.** `?view=all|pricing|add|groups|add-group|rules|publish|inventory|edit|edit-group`. The row reads **All | Pricing | +Add Service | Group | +Add Group** and, after a thin divider, **Price Rules | Shop Publish | Inventory** (the three views the console has beyond the layout). `edit` (one service, `?view=edit&id=<id>&part=overview|pricing|fields|api|shop|inventory|activity`) and `edit-group` have no link. A view the role may not use, or an unknown one, replaces the address with the first view the role may use, so no view is ever mounted (or its data read) for a role that cannot use it. A view is one row of a registry (`lib/productsViews.tsx`) and a part of the edit view one row of another (`lib/serviceParts.tsx`): a package adds its row and nothing else.
- **One address builder.** `productsPath` (`src/features/services/lib/productsPath.ts`) writes every address of the page in one fixed key order and leaves defaults out (the first page); links inside the app use it, so they never take a redirect. It replaces `catalogPath`, which is gone. The keys: `view`, `type`, `id`, `part`, `group`, `q`, `api`, `show` (the list's quick filter: attention, offshop, disabled), `page`, `size`, `supplier`, `from`, `return` (+Add Group: `add` goes back to +Add Service after Add), `run`, `tab` (Price Rules: merchant, shop, check). The storefront feature's `storefrontPublishPath`, `storefrontPricingPath` and `storefrontOnShopPath`, the audit and dashboard links, the palette's service search and the Suppliers page's "Add services from this supplier" call it.
- **Old addresses redirect for good.** `legacyTarget` (`src/app/legacyRedirects.ts`) maps `/catalog`, `/services` and the Storefront tabs that moved to the new page, carrying what each view reads: the table keys (`q`, `type`, `page`; `categoryId` becomes `group`, `supplierId` becomes `api`; the chips and `belowFloor=true` become `show`) to `view=all`; `?open=<id>&section=…` to the edit view's part; `?add=<supplier>|new&from=…` to `view=add`; `?view=settings&tab=categories` to `view=groups`; `tab=rules|shop-prices|resolver` to `view=rules&tab=merchant|shop|check`; `tab=inventory` to `view=inventory`; `?view=publish[&run=N]` to the same; `/storefront?tab=publish|pricing|listings` to the publish view, the shop price rules and the list. The backend's mail about waiting shop price changes keeps linking to `/catalog?view=settings&tab=shop-prices`, which now reaches `/products?view=rules&tab=shop`. The routes and the table of cases are data in `legacyRedirects.test.ts` and `legacyRoutes.test.tsx`.
- **What was removed.** The Catalog page and everything that only served it: the page, its table, chips, bulk bar and shop switch cells, the side panel and its six sections with the question before unsaved changes, the settings view and its tab strip, the Add services host and its multi-step dialog (the suppliers feature's `addFlow`), the panel's Suppliers section and its dirty reporting, the storefront feature's panel adapters, the publish tab's own address hook, the kit's `SidePanel` and `Steps`, `catalogPath` and the Catalog filters of the address, the list and count hooks of the table, and the tests that reached only these. With the views built, also what they replaced: the Categories tab and its dialogs, the dialogs that edited one thing of a service (Edit price, Group prices, Fields, Options, the New/Edit service dialog with its details body, quantity fields and new-category step), `LoadGate`, `LinkedSuppliers`, the pre-Catalog "Services on sale" table of the storefront feature (`ListingsTab`, `ListingTable`, `ListingStats`, `ListingsEmpty`, `PublishServicesButton`, `ListingCreateDialog`, `ListingEditDialog`, `PriceDialog`, `PriceFormBody`, their search fields, thumbnail and price tag, their test host and tests), the hooks only they used (`useCreateService`, `useSetExecutionMode`, `useSetListed`, `useCreateListing`) and the stand-ins of the views and parts (`BeingBuilt`).
- **What is reused.** Every API function, type, mock route and the mutation hooks the views call; the choice hooks (services, categories, groups, merchants, suppliers); the form logic as hooks and pure helpers (`useEditPriceForm`, `useGroupPricesForm`, `lib/serviceDetails.ts`, `lib/quantity.ts`, `lib/fields.ts`, `lib/options.ts`, `lib/priceForms.ts`), the supplier links draft and save, the storefront's `ListingFormBody` and `shop/priceForm.ts`; the one shop switch (`usePutOnShop`, `lib/shopSwitch.ts`) and the bulk runner (`src/lib/bulk`, now `useServicesBulk`); the kit's `FormSection` and `BulkSummaryDialog`; `src/lib/serviceTypes.ts`; the merchant price rules, the shop price rules (with the proposals that wait), the price check, the code stock and the publish runs, which the three extra views mount as they are; the older Quick add and Import dialogs of the Suppliers page; the Delete service and Bulk price dialogs (a small confirm question and the bulk price change).
- **All.** The first view: a "Quick Search" box (Select Group, the search text with its Search button, then the API menu (the primary supplier connection) and Show: all services, those that need attention, the active ones not on the shop, the switched-off ones), one refresh tool, a dense table in the list skin (checkbox; Service Name with "#<id>" and the code in small italics and, in the critical colour, the server's attention words; API with "then <fallback>" under it; Group; Status and Shop as small squares that are buttons; Actions with the square-pen link to the edit view), the "With selected" strip (Enable, Disable, Put on the shop, Take off the shop, Move to group + Apply, Delete with a confirm question, one call per service through `useServicesBulk`) and the pinned footer (Results, Go To, the pager, Page size 25, 50, 100 or 200, default 50). Every filter, the page and the size live in the address; the list is in the stored order, the one merchants see (`_sort=sort`: the group's position, then the service's own position, then the name), so the order saved with Set Order shows here too; the server filters and counts. The Shop square is the one shop switch and exists only for a role that may read the shop; it is as narrow as the Status square, and the server's reason a service cannot go on the shop is written under the name (and is the locked square's hover text). The view keeps its address (filters, page, size) for the session per kind (`all/lastAllAddress.ts`), so the editor's Back to All, the links back from its empty states and the move after a delete return to the list as it was last seen.
- **Pricing.** The price grid on the server's one read of the figures (`GET /admin/services/price-grid`, backend decision 063): a Quick Search box (search, group, "USD - Base", and at the right "Display Enable/Disable Service" and "Set Order"), then per service the layout's read-only Purchase Cost box (empty, with a title saying the cost comes from the supplier connection, for a service with a supplier; filled with the cost on record only for a service with none), the API price (the supplier's figure in bold, with the tick while in step and the supplier's name as the tick's title, or the arrow and the old figure when it moved), the base price with its margin, the shop price with its source and margin and one price per merchant rank with its margin (each column headed "<rank> [USD]"), all as the server sent them. The grid always reads the stored order (`_sort=sort`), so Set Order shows its effect at once. The server's word for a typed shop price is `manual` (the same as the service rows); the grid prints it as "typed". "Display Enable/Disable Service" puts a box before each service's name (no column of its own). Prices are typed in place and marked "Unsaved"; while a price or a position is typed, the editor's `UnsavedGuard` asks before a link leaves the view (another kind, another view, the "$" tool) and the browser asks before a reload. One pinned bar holds Save prices (planned by `lib/priceGrid.ts`, sent row by row through the existing routes: the base price, then the group prices with the shop price as the row showed it and `retailPriceSeen`), Bulk change… and, with Set Order, Save order (`POST /admin/services/order`), above the footer of the list in the same bar. Bulk change stays a dialog in this version (a form, then the server's preview); it opens on the grid's kind (only that kind's groups are offered) and on the grid's group when one is chosen. A later version moves it into the grid's Quick Search box with the preview drawn in place.
- **+Add Service.** A heading, the checkbox "Add services from a supplier" (its state is the address: `?supplier=` and `?from=`) and one of two forms. By hand: label-left rows in the layout's order (Service Name with "- Select -" that copies an existing service's settings, Code, Service Listed In Group with "Add New Group", Status, Send For Verification with its window in hours, User Can Cancel Order, Delivery Time with its unit, Credit in USD, Order handling) and the pinned Add; one create call, then one update only for Inactive or Manual; the edit view of the new service opens after it. "- Select -" never copies a value the role cannot send: without `catalog:update` Status and Order handling are not copied, and the hint says so. "Add New Group" keeps what was typed: the form is kept in the session per kind (`add/groupHandoff.ts`), the link opens +Add Group with `return=add`, and after Add that view goes back to +Add Service with the new group chosen; the draft is used once. Ticked: the suppliers feature's `AddFromSupplierForm` (taken through its index by `AddServiceView`), one label-left form with no dialog and no steps: Supplier, Add (Whole groups | Single services), the picker in place (the groups of the kind with To add, In console and Cannot add; or a Quick Search box, the supplier's services with Check All and an inline pager, and a Preview button), Service Listed In Group, Status, Put on the shop and the pinned Add; whole groups start the quick add run, single services are imported 500 at a time with the chosen status and group (decision 063); progress and result show in place, above the pinned bar. The view hands the heading and the checkbox to the form as its `header`, drawn inside the form's frame, and draws no result line of its own. In the single-services picker, "Check All / Uncheck All" and Preview sit directly under the table and the pager after them; Check All never ticks a service of another kind, also when the supplier spells the kind more than one way.
- **Group, +Add Group, edit-group.** The groups of the kind as a list (checkbox, Group Name, up and down buttons that save the position, the status square, "Visible to", the number of services, the square-pen link), "With selected" (Activate, Deactivate, Delete with a confirm question) and the footer pager; +Add Group and edit-group are one label-left form (Group Name, Active as Yes | No, Visible to as "All ranks" and one box per rank) with Add or Save pinned. The kind of a group is the strip's and cannot move.
- **The edit view.** `EditView` reads the address, `ServiceEditor` reads the service (loading, a 404 told apart from a failed read with Retry, and a move of the strip to the service's own kind), `OpenService` draws `PartsLayout` (the name, "#id · code", Back to All, the parts the role may see) and holds the question before unsaved changes. A part says it is unsaved through `onDirtyChange` (the kit's `useReportDirty`, or `useDirtySections` for a part of several sections); `UnsavedGuard` asks before a click on a link opens another part, view or page, and the browser asks before a reload; moves made by code and Back/Forward are not held back (the app has no data router). A part saved as a whole is a `PartForm` (the fields and one pinned Save): Overview (in the order and shape of +Add Service: name, code, group, status, verification with its window as a row of its own, cancel, delivery time, order handling), Set Pricing (credit and minimum profit with the server's cost, floor and margin read-only, then each merchant rank's fixed price and what it pays now; the price first, then the rank prices) and API Connection (the suppliers feature's `ApiConnectionPart`: the primary connection with a server-side search of the supplier's services, the secondary ones in order, one Save replacing the whole chain). A part of independent sections has a `SectionForm` per section with its button under its rows: Field (Quantity Field, Custom Fields, Options), Retail Purchase (the storefront feature's `RetailPurchasePart`: On the shop with the one shop switch as a Yes | No control, Shop price by rule or typed, the waiting price change, Shop page) and Inventory (counts, Import codes, the stored codes with the footer pager). Activity links to the service's orders and its price check and holds Delete. The parts of other features are mounted by thin adapters of the services feature and take plain props. A part never works from a stale copy of the service (`edit/usePartStart.ts`): a part that fills a form from the record (Overview, Set Pricing, Field, Retail Purchase) is not drawn while the record is being read again, and a part that holds nothing unsaved starts again from the new record when the record changes; a part with unsaved changes keeps them and the copy it started from, and the record that follows its own save is taken without starting again (so "Saved" stays).
- **The three extra views.** Price Rules, Shop Publish and Inventory follow the same grammar: no card, no tab strip and no count chip (the sub-views of Price Rules are the kit's `ViewLinks`, the waiting proposals told as plain words on the Shop price rules link), status squares or plain words instead of badges, lists that end in the footer pager, and the primary action (New rule, Import codes…) in the pinned bar. Inventory is drawn from the Inventory part's pieces (a Quick Search box, the refresh tool, the status squares, "With selected", the footer pager). Their editors stay dialogs in this version: the merchant and shop rule dialogs with their delete and turn-off questions, Import codes and Void codes, the publish preview's row dialog, its bulk dialogs and the Publish confirm.
- **The frame.** The page is one frame as tall as the window (`.page-frame`): the heading and the two rows of links keep their height and the view takes what is left, so a short view ends with its pinned bar at the foot and nothing scrolls; the right column of the parts layout does the same.
- **Carried over from decision 019.** Shop content stays a page of its own in the System group (its gate has no `pricing:read`); old addresses redirect for good through one pure function with a test per case, wired before a page's gate; one builder writes every address of the page; the page's gate is "any one of" its read permissions.
- **The kit.** The page is drawn from kit pieces (`StripTabs`, `ViewLinks`, `LegendBox`, `FooterPager`, `PinnedBar`, `YesNo`, `FormRow` and the `layout="row"` of the fields, `SectionHeading`, `PartsLayout`, `StatusSquare` and `SquareToggle`, `WithSelected`, the `list` skin of `DataTable`), which use the tokens only, so both themes work. What two view packages built for themselves was lifted into the kit when the views were joined: `PartForm` (a part saved as a whole, with `SaveBar`, its pinned primary button, the reason it is off, "Saved" and the failure), `SectionForm` (a section saved on its own, its button in the control column or under a table), `SavedStatus` and `SaveFailure`, `useSaveFlow` and `outcomeOf` (the run of one Save, which `FormSection` now uses too), `useReportDirty` and `useDirtySections` (a part's unsaved report), `ReadValue` (a read-only figure in a row), `RefreshTool` (the tool row above a list), `QuickSearchText` (the search text and its Search button) and two placements of `FooterPager`: `actions` (the view's buttons above the footer in one pinned bar) and `inline` (a plain footer inside a form whose own bar is pinned). The old `Pager`, `DataTable` and the fields behave as before.
- **Names.** Nothing of live code is named after the Catalog page any more, except the sidebar group and the server's `catalog:*` permissions: the bulk runner is `useServicesBulk`, the refresh after a row action `useServicesRefresh`, the shared key of the services rows `SERVICE_ROWS_KEY` (`['api', 'services', 'rows']`), the category and client-group types `types/categories.ts`, the services mock's join of the other mocks `mocks/serviceFacts.ts` and the storefront mock's reader `mocks/shopFacts.ts`.
- **Left out on purpose.** The layout has "Assign This Service To User", a notice to a chat channel (and a Telegram column in the group list), export and print tools above the services list and adding services by a file; the console has no data or route for the first four and offers the fifth as "Add services from a supplier". The three order switches of a service (`allowCancel`, `allowVerify`, `verifyWindowH`) are typed in the console, because the server has always sent and accepted them. Where the console differs from the layout or the backend for a reason, MISMATCHES says so (M268 to M277, M300 onward).

**Consequences.**
- A role with only `pricing:read`, `inventory:read` or `storefront:read` opens the page and lands on the first view it may use, as in decision 019.
- The views were built in parallel against the registries, then joined: each registry row now names the real view or part, the stand-ins are gone, and a view or a part is still one folder or file and one row.
- The tests that used to reach a dialog or tab through the Catalog page moved with what replaced it: each view and part has its own page-level tests against the mock API, the three extra views are reached through the new page's address, and the kit pieces have their own tests.
- An address of the page is a change to `productsPath` and to the table of redirect cases; nothing else in the shell changes.
- Backend: the price-grid read, the stored order of services and the supplier import options are the backend's decision 063, typed by the console as the views use them (MISMATCHES M308 to M313). Settled: the All list and the price grid follow the stored order; a typed shop price is `manual` on every wire (the backend's two allowlist entries for the grid's old word can go). Open: an `id` filter on the price grid for the Set Pricing part, a `serviceId` filter on the orders list, a data router to hold Back and Forward while a part or the grid is unsaved, and (a later version) the bulk change inside the grid's Quick Search box and the dialogs of the three extra views drawn as views.
