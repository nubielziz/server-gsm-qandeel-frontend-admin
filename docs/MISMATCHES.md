# Mismatches

Where the demo (`reference/gsm-admin`) and the map (`reference/gsm-map`) disagree, or a source contradicts itself.
Precedence: API shape, entities, permissions and error codes follow the **map**; screens, layout, copy and interactions follow the **demo**.
Every row says what differs, which source we followed and why. Nothing is picked silently.

| # | Area | Demo | Map / other source | Followed | Why |
|---|---|---|---|---|---|
| M1 | Abandoned-cart reminders | Sends a reminder to every abandoned checkout that has an email. | `POST /admin/checkouts/recover` sends one recovery email, only to customers with marketing consent (`consent_records`). | Map | Consent is a legal rule the server enforces. The UI only offers the action for consented rows and shows the server's answer. |
| M2 | Design source | `design-system/gsm-supply-admin/MASTER.md` describes a dark theme, Fira fonts and a green accent. | `DESIGN.md`, `tailwind.config.cjs` and `input.css` (what the demo actually renders): warm light paper, IBM Plex, ink-black primary, one working blue. | `DESIGN.md` + demo CSS | The brief says keep the demo's look; MASTER.md is a generated draft the demo never used. |
| M3 | Merchant withdrawals | Finance page has a Withdrawals tab (pay / reject a withdrawal request). | Table `withdrawal_requests` exists, but no admin route reads or decides it. | Map | No endpoint to call. The tab is left out; the backend can add withdrawal routes later and the tab can be ported then. |
| M4 | Storefront checkout preview | Storefront page has a Preview tab that walks a fake customer through check, consent and pay. | That flow is the `store` surface (out of scope for the console). | Map + scope | Not ported as a simulation; replaced by a link to the live storefront (`VITE_STOREFRONT_URL`). |
| M5 | Sign-in screens | The demo has no sign-in, 2FA or set-password screens (it starts signed in). | Map defines login → TOTP, first-time TOTP setup, and invite/reset links. | Map | New screens built in the demo's visual language. Request/response bodies are assumptions (decision 006) until the backend confirms them. |
| M6 | Auth request/response bodies | – | The map names the auth routes but not their bodies (`login` next step, `2fa/setup` QR format, `me` fields, CSRF token source). | Assumption | Documented in decision 006; each assumption lives in one function so a different answer is a one-file change. |
| M7 | Permission per CRUD operation | Demo role matrix grants areas, not actions. | CRUD rows carry `x:*`; action rows carry `x:action`. | Map + assumption | `x:*` on a CRUD row is read as `x:read` (list/show), `x:create`, `x:update`, `x:delete`; a granted `x:*` matches all. Server enforcement decides in the end. |
| M8 | Queues monitor | – | `GET /admin/queues` is the Bull Board UI, not JSON. | Map | Exposed as a link that opens in a new tab; the typed function builds the URL instead of fetching. |
| M9 | Demo-only controls | Sidebar footer says the data is synthetic; topbar "Demo" menu switches data state (normal/loading/empty/error) and simulates orders, storefront orders, tickets, supplier outages and data reset; the palette has the same simulations. | – | Brief | Not ported. The footer shows API health (`GET /health`); loading/empty/error come from real query states; only the menu's Display section (theme, compact rows) survives as a "Display" menu. |
| M10 | Request and response bodies | Demo dialogs show which fields each action collects. | The map lists routes, permissions and tables, not bodies (except the order and error examples). | Demo fields + schema columns | Every typed function whose body is not fixed by the map says "Assumed contract" in its JSDoc; the backend confirms or the type changes in one place. |
| M11 | Roles | Six fixed roles (Owner, Admin, Finance, Support, Risk reviewer, Read only) with an area matrix. | `CRUD /admin/roles` with free `permissions text[]` and `GET /admin/permissions`. | Map | Roles are editable records whose permissions come from the server; the demo's matrix is kept only as the visual layout of the roles tab. |
| M12 | Temporary passwords (admins) | The admin types a temporary password (or presses Generate) in the dialog, with a length and strength check on the client. | The map says staff get an invitation or a temporary password and that the current password is never readable; it gives no body. | Assumed contract | The server makes the temporary password and returns it once (`temporaryPassword`); the console shows it in a one-time dialog with a copy button. There is no typed password, no Generate button and no client strength check: the server owns the rule. |
| M13 | IP verdicts | `ipVerdict` decides in the browser from the local rule lists: the address tester, the "Blocked" / "Not on the allowlist" chip and the "Your address is allowed by…" line. | `POST /admin/ip-rules/check` returns the decision and the matching rule. | Map | The tester, the chip and the "Your address" line ask the server. `parseIp`, `ipIn`, the range-width check (/16 or narrower) and the own-address checks stay in the browser as hints only. |
| M14 | Restriction state | `S.access.restrict`, one flag in the page state. | "Restricting the console to the allowlist is a switch in settings"; `PUT /admin/access/restriction` changes it, and no route reads it except `GET /admin/settings`. | Assumption | The state is read from `GET /admin/settings`, key `adminAllowlistOnly` (assumed). Reading it needs `settings:read`; without it the switch is disabled and says why. |
| M15 | "Your address" | A fixed `MY_IP` constant. | No route tells the console which address the current request comes from. | Assumption | `me.lastLoginIp` stands in for it (guards for turning the restriction on, removing the rule that lets you in, and blocking your own range). The server still decides every case. |
| M16 | Invitation time | `resetSentAt` on each admin gives "Invitation link sent 5m ago" and "The invitation link expired". | `staff_users` has no such column (the one-hour links live in `auth_tokens`). | Assumed contract | `StaffMember.resetSentAt` is an optional extra field. Without it the drawer only says that an invitation was sent and that a new one can be sent from Password. |
| M17 | Removing an allowed IP | `removeIpRule` refuses any removal of an allowed rule while no other live rule covers your address, even a rule that does not cover you. | The map only says the server may reject requests that would lock the caller out. | Demo, narrowed | The hint applies only when the rule being removed covers your address and no other live rule does. It shows in the confirm dialog (with the demo's wording) and stops the request; the server's own refusal is shown the same way. |
| M18 | Owner role | A fixed `owner` role: "keep one active Owner" counts accounts with that role. | Roles are free records; the map says only that the last Owner cannot be suspended. | Assumption | An Owner is a member of the role named "Owner" or of any role with the wildcard permission `*`. The hints (cannot suspend or demote the last active Owner) use this reading; the server enforces its own. |
| M19 | Access page gate | The demo shows Admins and access to Owners (and read-only to Admins). | Its tabs need different permissions (`staff:read`, `access:read`, `roles:read`, `sessions:read`). | Map | The page opens with any one of them and each tab shows only what the role may read; a role with none sees the no-access page. |
